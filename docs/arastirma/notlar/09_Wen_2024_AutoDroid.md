# 09 AutoDroid: LLM-powered Task Automation in Android (Wen 2024)
**Type:** system (with benchmark DroidTask) · **Relevance:** high

## Core contribution (2-3 lines)
An LLM-driven agent that automates arbitrary tasks on unmodified Android apps. It explores each app offline to build a UI Transition Graph, synthesizes "simulated tasks" as app memory, and at runtime prompts an LLM (GPT-3.5/GPT-4 or on-device fine-tuned Vicuna-7B) with a compact text UI representation to choose the next action. Evaluated on DroidTask (158 tasks, 13 apps).

## Key findings (bullets, with numbers)
- GPT-4: 90.9% action accuracy and 71.3% task completion; +36.4% and +39.7% over the LLM-framework baseline (abstract).
- Vicuna-7B fine-tuned on app memory runs on a phone (Snapdragon 8 Gen2): 57.7% action accuracy, 41.1% completion (with CoT and MoTiF data).
- Mean prompt length cut from 625.3 to 339.0 tokens; GPT-4 cost per 1000 queries from $18.76 to $10.17.
- LLM calls account for 77.6% of GPT-4 per-step latency and 87.1% of on-device Vicuna latency.
- Action space cut from 36.4 to 13.2 choices per GUI state.
- Shortcuts (embedding match to memory) avoid LLM calls in 75% of cases where they apply; 38.02% of steps saved.
- Risky-action detection: precision 75.0%, recall 80.5%. Privacy filter plus security confirmation lowered GPT-4 accuracy from 92.9% to 89.9%.
- Offline preparation: 0.5-1 hour per app for the UTG, plus 5-10 minutes of LLM synthesis.

## Implications for our app (bullets; tag each)
- [AGENT] Keep app-specific memory of successful routes so repeated tasks can run without LLM calls.
- [LATENCY] Skipping LLM calls for known steps cuts both cost and delay; this supports "learned tasks replayed without AI".
- [SAFETY] Ask the LLM to flag actions that change user or server data, and also flag warning text on screen; confirm before calls, sends, or purchases.
- [PRIVACY/KVKK] Mask personal data (names, phone numbers, emails) before any cloud call and restore it locally.
- [ELDERLY] Multi-step tasks are the main failure source; the failure modes (premature "done", misread GUI) must be guarded in a narrated, interruptible flow.
- [VOICE] The paper is text-only; voice input and output are ours to design.

## Techniques we could reuse (concrete)
- Simplified HTML-style UI prompt: five element types (button, checkbox, scroller, input, p) with ID, label, text, and onclick hints; merge plain-text siblings under one clickable parent with a line break.
- Output constraint: "id=<n> action=<tap/input> input text=<text or N/A>", with id=-1 meaning task done.
- Exploration-based memory: random UI exploration, then the LLM summarizes each element's function, stored as (simulated task, UI states, elements).
- Retrieve top-k memory entries by Instructor-XL embedding similarity; inject hints only for matching UI states.
- Auto-scroll scrollable containers before prompting to avoid extra LLM calls.
- Temperature 0.25; zero-shot CoT fine-tuning data generated by a larger model.

## Risks / warnings the paper raises
- Latency limits practical use; LLM calls dominate runtime.
- Multiple valid paths can be marked wrong; premature completion detection errors.
- Cloud use of GUI text raises privacy concerns even after masking.
- Full UI text can reach about 40k tokens per UI state, so trimming is required.
- Small local model is weaker than cloud models; input actions were poor without extra annotated data.

## Evaluation ideas (metrics/protocols we could use to evaluate our app)
- Action accuracy (correct element and input text per step) and task completion (all steps correct).
- Cost per 1000 queries and tokens per prompt.
- Per-step latency split into LLM, embedding, and execution, measured on the target phone.
- LLM calls saved per task by memory shortcuts.
- Risky-action precision and recall on a labelled set of sensitive actions.
